# Pipeline and Sourcing pages (`/pipeline`, `/sourcing`)

The deal funnel is split across two sidebar pages, both gated by `PIPELINE_ENABLED`:

- **Sourcing** (`/sourcing`) holds deals that are not yet in L0. Its **Pending Confirmation** tab lists unreviewed inbound deals (`pipeline_stage = 'unreviewed'`) with search, an Origin (document type) filter, the triage banner and the Triage Unreviewed modal. Its **AI Market Scanning** tab holds the market-scan status and the AI-discovered companies. `?tab=scanning` opens the second tab.
- **Pipeline** (`/pipeline`) holds the deal table. The stage filter offers All Stages (the default), each of the workspace's stages (see below), and a Pending Confirmation chip that shows the same unreviewed bucket inline. The dropdown row picks the source (inbound or outbound table), the status (active or dropped), the tracks, the sort and the columns. `?stage=` takes `all`, `pending` or a stage key; the parsing, matching and per-stage counting rules live in `src/lib/pipeline/stageView.ts`.
- **Pipeline search** combines with the stage filter. The first keystroke widens the filter to All Stages; each stage tab and the Pending chip then show how many matches they hold, and clicking one narrows the results without clearing the search. Clearing the search restores the stage the user started from, unless they picked another stage mid-search. When the other source's table also has matches, a "N matches in Outbound — Show" line switches to it. The search text lives in `?q=` (written with `history.replaceState`, so typing adds no history entries).

`src/views/Sourcing.tsx` renders `Pipeline` with `page="sourcing"`, so both pages share one data load, the same row actions and the same dialogs (company detail, update, promote/demote, drop, triage).

## Configurable pipeline stages (MB-651)

Each workspace names, numbers, describes, orders, adds and deletes its own deal stages, from **Pipeline Settings → Pipeline Stages** on the Pipeline page (the Pipeline Settings dialog, beside Investment Track and Required Fields).

- **Storage.** `pipeline_stages` holds one row per workspace stage: `key`, `code` (the editable number, e.g. `L3`, unique among live stages), `name` (≤ 40 chars), `description` (plain text), `position` and `deleted_at`. A trigger on `workspaces` insert seeds the six defaults (L0 Company Sourcing … L5 Closing), so every insert path gets them. `companies.pipeline_stage` is text: a stage `key`, or one of the fixed pre-pipeline buckets `market_screening`, `unreviewed`, `discovered`.
- **Keys never change.** The six original stages keep the keys `L0`–`L5`; added stages get `stg-<hex>`. Renaming or renumbering a stage changes only `code` / `name`, so companies, logs and links stay valid.
- **Rules stay on their stage.** The L0 entry checks and track matching, and Acquired-at-L5, follow the original key wherever the stage is moved. Range rules follow position: the Deal Captain applies from L3 onward and the stale-deal SLA covers L0 through L3, in the workspace's order (a stage added after L3 is a Captain stage).
- **Screening promotes into the stage after L0.** AI screening is the gate out of L0, so its promote (the Screening Progress panel) targets whichever live stage follows L0 — L1 by default — and the screening-result filter sits on that stage's tab. Deleting, moving or inserting a stage before L1 never strands it; only a workspace with nothing after L0 loses the promote. Helpers live in `src/lib/pipeline/stages.ts` (`screeningTargetKey`, `stageKeysFrom`, `stageKeysThrough`, `isInPipelineStage`).
- **L0 is locked**: it can be renamed but not moved or deleted, because confirmed deals enter there and demoting out of it returns a deal to Pending Confirmation.
- **Deleting** a stage moves its active deals to a stage the user picks (logged as ordinary `PROMOTED_FROM_x_TO_y` moves) and soft-deletes the row. Dropped deals stay at the deleted stage and keep its name; restoring one asks which stage to restore it to (`restore_stage_required`), and the resurface cron brings one back at L0. No move, bulk move or Current Stage edit can target a deleted stage.
- **Code.** `PipelineStageService` (`/api/pipeline-stages`, `/api/pipeline-stages/[key]`, `/api/pipeline-stages/[key]/move`) owns the changes; views read the stages through `usePipelineStages()`; the agent tools accept any stage key and `list_pipeline_stages` maps the codes users say to keys.

## Configurable pipeline required fields

Each workspace chooses which fields a company must have before it can enter the pipeline (its first stage), from **Pipeline Settings → Required Fields**.

- **Storage.** `workspaces.pipeline_required_fields` (nullable `text[]` of `PipelineFieldKey`s; migration `20261019000006_add_workspaces_pipeline_required_fields`). `NULL` means the product default — every field (Company/Project Name, Entered By, Inbound/Outbound, Deal Type, Geo, Sector, Banker) — so existing workspaces keep the original rules. Saving the full set writes `NULL` again, so a field added to the product later is required by default.
- **The name is locked.** Company Name / Project Name is always required (`ALWAYS_REQUIRED_PIPELINE_FIELD_KEYS`); a company with neither is unaddressable. Banker keeps its rule when required: inbound deals only.
- **One definition, enforced server-side.** `src/lib/pipeline/requiredFields.ts` holds the field list and `normalizePipelineRequiredFieldKeys`. `CompanyService` reads the workspace's set once per request (`setWorkspaceRepo`) and applies it on every pipeline entry: promote, bulk triage, the Current Stage dropdown, Smart Files approval and Pending auto-promote; a miss throws `CompanyPipelineRequirementsError` (422 with `missingFields`). `GET/PUT /api/pipeline-required-fields` reads and saves it.
- **Not retroactive.** Changing the set affects the next entry into the pipeline; companies already in it are untouched. The Pipeline "Add Company → Manual" form keeps its own fixed required set.

## Configurable page heading (title and subtitle)

The Pipeline page's **title and subtitle** are a workspace setting, not fixed product copy: a workspace that calls the page something else ("Acquisitions" / "Live targets only") renames it in place for everyone. The pencil button beside the title opens `PipelineHeadingDialog`.

- **Storage.** `workspaces.pipeline_title` / `workspaces.pipeline_subtitle` (nullable text; migration `20261007000001_add_workspace_pipeline_heading`). `NULL` means "use the product default" — `Deal Pipeline` / `Track companies through all stages` — so an untouched workspace renders the original copy and **clearing a field restores the default** rather than leaving a blank heading.
- **Shared rules.** `src/lib/pipeline/heading.ts` is dependency-free and used by both sides: `resolvePipelineHeading` (columns → rendered heading), `parsePipelineHeadingInput` (untrusted payload → values to store: trims, blank → `null`, max 80 / 160 chars), and the default strings themselves.
- **Backend.** `WorkspaceService.getPipelineHeading` / `updatePipelineHeading` → `/api/pipeline-heading` (`GET` the resolved heading, `PUT` to save). The workspace comes from the request context, never the body: the read uses `getActiveWorkspaceId()`, the write `getActiveWorkspaceIdOrThrow()` so it fails closed with a 403 instead of stamping the no-active-workspace sentinel into an `UPDATE`.
- **Authorization.** Any signed-in **member** may read and write — the same call as [workspace table layouts](workspace-table-layouts.md), and deliberately looser than [the display currency](workspace-display-currency.md), which is superadmin-only. The trade-off is last-write-wins with no in-app audit surface.
- **Frontend.** The `/w/[workspaceSlug]` layout resolves the heading from the workspace row it has **already** fetched (no extra query) and provides it via `PipelineHeadingProvider`, keyed by slug, so the page paints the custom copy on first render instead of flashing the default and so switching workspace remounts rather than showing the previous one's heading. `Pipeline.tsx` reads it with `usePipelineHeading()`; saving repaints the header from the server's resolved response.
- **Sourcing keeps its own fixed heading** ("Sourcing" / "Candidates not yet promoted into L0 sourcing"), and the copilot's page-context string still describes the page in canonical pipeline terms, so renaming the heading never changes what the agent is told it is looking at.
