# Insight generation (always on the AI Workforce, with an email when it is ready)

## Chat never creates an insight

Every new insight — a report, a dashboard, an interactive tool, a one-pager, or
an insight built on a template — is generated by the AI Workforce. No chat tool
list (`chatOnlyTools`, `investmentTools`, `vcTools`, the combined list, or
`SECTOR_CHAT_CORE_TOOLS`) carries `propose_insight_create`; the chat prompts
(`INSIGHT_AUTHORING_GUIDE` in `src/lib/agents/analysis/guides.ts` — the routing
half; the rules for the document itself are `INSIGHT_EDIT_AUTHORING_RULES`,
carried by `propose_insight_edit`'s description because that tool loads on
demand — and the template blocks in `src/lib/insights/largeDocument.ts`) tell
the model to call
`propose_workforce_handoff` with an instruction that says what the insight
covers, its kind, and anything the user specified. Reports still go through
`propose_report_plan` first; the confirmed plan becomes the handoff instruction.

Editing an existing insight stays in chat: an edit confined to one `data-section`
block is read and proposed as that block alone (`get_insight` / `propose_insight_edit`
with `section`, see `insight-section-editing.md`), whatever the insight's size; only
an edit wider than one block on an insight too large for a chat turn goes to the
Workforce.

`propose_insight_create` itself is still exported so past transcripts that carry
its approval card keep rendering.

A handoff from a sector chat (`@minerba`, `@dikti`, `@bangun`) runs on the
general Workforce agent — non-refresh runs never pick a sector agent — so the
sector chat is told to put its sources, methodology and data limits into the
instruction.

## The "insight ready" email

`create_insight` stamps the run id on version 1 (`insight_versions.source_run_id`),
as `edit_insight_section` and `replace_insight_document` already did for later
versions. When a run finishes, `finalize` in `src/lib/workforce/runAgent.ts`
calls `EmailNotificationService.notifyInsightsGenerated(runId)`:

- It reads every live insight the run wrote with
  `InsightVersionRepository.findInsightsBySourceRunId` (one grouped query) and
  enqueues an `insights_generated` email to the run's recipient — the
  triggerer, or the routine's creator for a cron run — with a workspace-slugged
  link to each insight, marked created or updated.
- It is **not** gated by `TASK_NOTIFICATIONS_ENABLED` and is sent for cron runs
  too: once generation always happens in the background, this email is how the
  requester learns the insight exists.
- When it sends, the run's plain `task_completed` email is skipped, so the
  user gets one email. When the run wrote no insight, `task_completed` goes out
  as before.
- Scheduled refresh runs are excluded; they keep the owner-addressed
  `insight_refreshed` email.
