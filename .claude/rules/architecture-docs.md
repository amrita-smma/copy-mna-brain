# Architecture Documentation

How this repo's documentation stays true — and stays small — as the codebase
grows. The goal is orientation an agent can read in full on every task without
burning its context, which means those documents must stop growing even as the
codebase does.

## The four containers

| | `README.md` | `ARCHITECTURE.md` | `docs/architecture/code-map.md` | `docs/features/` |
|---|---|---|---|---|
| Content | What this is, how to run it | Shape: layers, request path, hazards | Facts: every route, service, repo, agent, job, flag, page | How one feature works |
| Author | Hand-written | Hand-written | Generated by `scripts/build-code-map.ts` | Hand-written |
| Changes | Rarely | A few times a year | Every week | When that feature changes |
| Grows with | Nothing | Number of *concepts* | Number of *files* | Number of *features* |
| Size limit | ~150 lines | ~400 lines | none (generated) | none (one file each) |
| Enforced by | Review | Review | `pnpm arch:map:check` in CI | Review |

**Why four and not one.** This repo's README grew from 1.4KB to 182KB in six
months — 125× — because `CLAUDE.md` said "update the README when an
architecture change happens" and the `pr-review` skill enforced it. Every
agent doing architectural work appended to one file. The content was not even
wrong (97% of its file references still resolved); it was correct
documentation in a container that could only grow.

Splitting the file without redirecting those instructions would have achieved
nothing. The containers above work because each has a *different* write
trigger, and `CLAUDE.md` §Overview routes changes to exactly one of them.

**The load-bearing invariant: anything countable is generated, and anything
feature-specific is its own file.** Those two rules are what bound the size of
the documents an agent must read on every task.

If you find yourself typing a list of files, a count, or a per-route table into
`ARCHITECTURE.md`, stop — either it belongs in the generated map, or the
generator needs a new section (see below). If you are writing more than a
paragraph about how one feature behaves, that is `docs/features/<feature>.md`.

## Regenerating the map

Run `pnpm arch:map` and commit the result whenever you add, remove, or rename:

- an API route (`src/app/api/**/route.ts`) — or change which HTTP methods it
  exports, or which container services it destructures
- a service or repository (`src/lib/services/`, `src/lib/repositories/`), or a
  key on the `Container` interface
- an agent or an agent tool (`src/lib/agents/<agent>/tools/`)
- a job handler or a `job_type` enum value
- a feature flag in `src/lib/flags.ts`
- a page (`src/app/**/page.tsx`)
- a migration

In practice: if you touched any of those, run it. It takes under a second and
is a no-op when nothing changed.

CI runs `pnpm arch:map:check`, which regenerates in memory and diffs against the
committed file. A stale map fails the build — this is what keeps it honest, so
do not weaken the check to a warning.

**Never hand-edit `docs/architecture/code-map.md`.** It carries a
`GENERATED — DO NOT EDIT` header and your change will be overwritten by the
next `pnpm arch:map`. To change what the map says, change the generator.

## Editing `ARCHITECTURE.md`

Edit it when the *shape* changes:

- a new top-level directory, or a new layer in the request path
- a change to how layers call each other
- a new cross-cutting hazard that has already caused a production bug
- a new rule file in `.claude/rules/`
- a new everyday command

Do **not** add:

- counts, inventories, or per-file tables → the generated map
- an enforceable rule with a review checklist → a file in `.claude/rules/`,
  linked from `ARCHITECTURE.md` in one line
- feature documentation, API payload shapes → `docs/features/<feature>.md`,
  plus a line in `docs/features/README.md`
- runbooks → `docs/runbooks/`
- history ("we used to…", PR numbers, incident IDs) → state the current rule

### Size budget

`ARCHITECTURE.md` must stay **under ~400 lines / ~20KB**. It is read in full on
most tasks, so every line is paid for repeatedly.

If a change would push it over, that is a signal the content belongs elsewhere —
not a reason to raise the budget. Move the detail to a rule file or `docs/`, and
leave a one-line pointer behind. A pointer an agent can follow costs ~15 tokens;
the section it replaces costs hundreds.

## The map records structure, never content

**Every field in the generated map must change only when the structure changes**
— a file added, removed, renamed, newly tested, a route's methods or wired
services changed. Never record anything that moves when a file's *contents*
change: line counts, byte sizes, function counts, TODO tallies, coverage
percentages.

This is not a style preference, it is what makes the CI check usable. GitHub
evaluates a pull request's **merge commit**, not its branch head. A
content-volatile field therefore goes stale on every PR the moment anything
lands on `main` that touches a counted file — so every open PR fails a check
about a file its author never opened, and the only fix is a regenerate-and-push
cycle per merge. A gate that fires on unrelated merges is a gate people turn
off.

This rule was written after a `Lines` column did exactly that: a service gained
six lines on `main`, and every open PR's map check went red.

## Extending the generator

When a genuinely new layer appears — a new kind of registry, a second agent
runtime, a new job system — add a section to `scripts/build-code-map.ts` rather
than describing the instances by hand:

1. Write a `collectX()` that returns plain rows. Use `tracked('glob')` for the
   file list so output stays deterministic and git-scoped. Record only
   structural facts (see above) — no line counts or other content-volatile
   fields.
2. Render it with the shared `table()` helper.
3. Run `pnpm arch:map`, eyeball the new section, commit both the script and the
   regenerated map.
4. Add the trigger to the "Regenerating the map" list above.

The generator is deliberately regex-based and dependency-free so it runs in CI
with no compile step. Keep it that way: it needs names and paths, not
semantics, and a parse miss should degrade one table row rather than fail the
run. Do not reach for the TypeScript compiler API.

## Reviewing a diff

Reject a diff that:

- adds a route, service, repository, agent tool, job handler, flag or page
  **without** a regenerated `docs/architecture/code-map.md`
- hand-edits `docs/architecture/code-map.md`
- adds counts, file inventories, or per-route tables to `ARCHITECTURE.md`
- pushes `ARCHITECTURE.md` past ~400 lines
- changes the request path, adds a layer, or adds a `.claude/rules/` file
  **without** updating `ARCHITECTURE.md`
- weakens `arch:map:check` in CI
- adds a content-volatile field (line count, size, coverage %) to the map
- adds feature documentation to `README.md` or `ARCHITECTURE.md` instead of
  `docs/features/`
- adds a `docs/features/*.md` without a line in `docs/features/README.md`
- reintroduces an instruction telling anyone to document architecture in
  `README.md` (that loop is what produced the 182KB file)
